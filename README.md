# TravelEquality

App para armar listas de equipaje y repartir el costo de un viaje.

La cuenta, las listas y el viaje se guardan en el servidor:

`https://viajelisto.onrender.com`

Al volver a iniciar sesión con el mismo correo y contraseña, se recuperan las listas y el viaje guardados en esa cuenta.

## Cómo abrirla

1. Instala Flutter.
2. En esta carpeta ejecuta `flutter pub get`.
3. Ejecuta `flutter run`. En el computador sirve `flutter run -d chrome`.

La dirección del servidor está en `lib/main.dart`. No hace falta levantar un servidor en tu PC.

La primera visita puede demorar cerca de un minuto si el servicio gratis de Render estaba dormido.

## Qué hace cada parte

- Equipaje: listas Playa, Camping y Bosque, y listas propias.
- Viaje: calcula combustible, peajes y otros gastos, y arma un texto para compartir con el equipaje marcado.
- Perfil: nombre, teléfono y foto de la cuenta.

Para comprobar que el servidor responde, abre `https://viajelisto.onrender.com/salud`. Tiene que decir `"ok": true`.

## Confirmación de cuenta por correo

Al registrarse, la app crea la cuenta sin esperar la entrega del correo y envía un código OTP de 6 dígitos en segundo plano. El código vence en 15 minutos; si no llega, puedes reenviarlo desde la pantalla de confirmación. En Render configura un proveedor de correo para el servicio:

- Brevo: `BREVO_API_KEY` y `MAIL_FROM` con un remitente verificado.
- Resend: `RESEND_API_KEY` y `MAIL_FROM` con un dominio/remitente verificado.
- SMTP: `MAIL_SERVER`, `MAIL_USERNAME` y `MAIL_PASSWORD`. Usa STARTTLS en el puerto 587; si falla, el servidor intenta SSL en el 465.

Si el correo no está configurado, el registro no activa la cuenta. Si un envío falla después de crearla, la cuenta queda pendiente de confirmación y puedes pedir otro código.

## Esquema de la base de datos

Este esquema define las tablas de usuarios, datos guardados y perfiles de Supabase Auth. El servidor crea su tabla `tokens` al iniciar para gestionar OTP, sesiones y recuperación de contraseña; por eso no aparece aquí.

```sql
-- Esquema usado por servidor/app.py. Las contrasenas se guardan como hash.
-- El servidor se conecta con credenciales privadas; no se exponen estas tablas
-- a los roles anon ni authenticated de Supabase.

create table if not exists public.users (
  id integer generated by default as identity primary key,
  name text not null,
  email text unique not null,
  password_hash text not null,
  phone text,
  photo text,
  verified integer not null default 0
);

create table if not exists public.user_data (
  user_id integer primary key references public.users (id) on delete cascade,
  lists_json text not null,
  trips_json text not null
);

-- Perfiles creados por Supabase Auth. Las contrasenas y los OTP permanecen
-- exclusivamente en auth.users.
create table if not exists public.profiles (
  id uuid primary key references auth.users (id) on delete cascade,
  email text not null unique,
  email_confirmed_at timestamptz,
  display_name text not null default '',
  phone text,
  photo text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
-- Complementa cada cuenta de Supabase Auth con sus datos visibles de perfil.

alter table public.users enable row level security;
alter table public.user_data enable row level security;

revoke all on public.users from anon, authenticated;
revoke all on public.user_data from anon, authenticated;

alter table public.users enable row level security;
alter table public.user_data enable row level security;
alter table public.profiles enable row level security;

revoke all on public.users from anon, authenticated;
revoke all on public.user_data from anon, authenticated;
revoke all on public.profiles from anon, authenticated;
grant select on public.profiles to authenticated;
grant update (display_name, phone, photo)
  on public.profiles to authenticated;

drop policy if exists "Users can read their own profile" on public.profiles;
create policy "Users can read their own profile"
  on public.profiles
  for select
  to authenticated
  using ((select auth.uid()) = id);

drop policy if exists "Users can update their own profile" on public.profiles;
create policy "Users can update their own profile"
  on public.profiles
  for update
  to authenticated
  using ((select auth.uid()) = id)
  with check ((select auth.uid()) = id);

create or replace function public.handle_auth_user()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  if new.email is not null then
    insert into public.profiles (
      id, email, email_confirmed_at, display_name
    )
    values (
      new.id,
      new.email,
      new.email_confirmed_at,
      coalesce(new.raw_user_meta_data ->> 'name', '')
    )
    on conflict (id) do update
      set email = excluded.email,
          email_confirmed_at = excluded.email_confirmed_at;
  end if;

  return new;
end;
$$;

drop trigger if exists on_auth_user_created on auth.users;
create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_auth_user();

drop trigger if exists on_auth_user_email_updated on auth.users;
create trigger on_auth_user_email_updated
  after update of email, email_confirmed_at on auth.users
  for each row execute function public.handle_auth_user();

create or replace function public.set_profile_updated_at()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

drop trigger if exists set_profiles_updated_at on public.profiles;
create trigger set_profiles_updated_at
  before update on public.profiles
  for each row execute function public.set_profile_updated_at();

insert into public.profiles (
  id, email, email_confirmed_at, display_name
)
select
  id,
  email,
  email_confirmed_at,
  coalesce(raw_user_meta_data ->> 'name', '')
from auth.users
where email is not null
on conflict (id) do update
  set email = excluded.email,
      email_confirmed_at = excluded.email_confirmed_at;

-- Aplicar el comando `git pull`
```
